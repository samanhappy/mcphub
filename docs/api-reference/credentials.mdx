---
title: "Credential Bindings"
description: "Manage the authenticated user's write-only credentials for shared MCP servers."
---

These endpoints operate only on the authenticated principal. There is no
username parameter and administrators cannot use them to read another user's
values. Server visibility and `server.invoke` authorization are applied before
any binding operation.

<Card title="GET /api/credentials" href="#list-credential-bindings">List visible credential templates and configured status.</Card>
<Card title="PUT /api/credentials/:serverName" href="#save-a-credential-binding">Create or rotate the current user's values.</Card>
<Card title="DELETE /api/credentials/:serverName" href="#delete-a-credential-binding">Delete the current user's binding.</Card>

### List credential bindings

`GET /api/credentials` returns metadata only:

```json
{
  "success": true,
  "data": [{
    "serverName": "personal-search",
    "credentialTemplate": {
      "env": { "SEARCH_API_KEY": { "label": "Search API key" } }
    },
    "complete": true,
    "configured": { "env": { "SEARCH_API_KEY": true } },
    "updatedAt": "2026-09-02T08:00:00.000Z"
  }]
}
```

Raw values and encrypted payloads are never returned.

### Save a credential binding

`PUT /api/credentials/:serverName` accepts declared, non-empty slots. Existing
bindings support partial rotation; the first write must provide every required
slot.

```json
{
  "values": {
    "env": { "SEARCH_API_KEY": "user-secret" },
    "headers": { "Authorization": "Bearer user-secret" }
  }
}
```

The response has the same metadata-only shape as the list endpoint. The next
tool invocation uses the new value; an existing stdio process for this exact
user and server is closed and recreated.

### Delete a credential binding

`DELETE /api/credentials/:serverName` removes only the current user's binding
and closes only that user's runtime for the server. Subsequent calls fail with
an actionable request to add credentials in **My Credentials**.
