## Overview

MCPHub supports [MCP Apps](https://github.com/modelcontextprotocol/ext-apps) as a transparent proxy. It forwards UI-linked tool metadata, app-only tools, `ui://` resources, and upstream list-change notifications. MCPHub does not render app UIs in its dashboard.

No MCPHub configuration switch is required. Support is enabled automatically when the downstream host advertises the `io.modelcontextprotocol/ui` extension with the `text/html;profile=mcp-app` MIME type. Legacy clients declare this during initialization; modern `2026-07-28` clients declare it on each request under `params._meta["io.modelcontextprotocol/clientCapabilities"]`. See the [protocol compatibility matrix](/api-reference/mcp-http#protocol-compatibility).

## Routing Requirements

MCP Apps passthrough is enabled whenever a request route resolves to at least one connected MCP upstream server:

- `/mcp/{server}`
- `/mcp/{group}`, whether the group contains one visible MCP server or several
- `/mcp` when at least one MCP server is visible to the caller

`$smart` routes are the one exception and continue to work as ordinary MCP routes, since Smart Routing tools aren't addressed by name at all. On that route MCPHub:

- hides app-only tools such as tools with `_meta.ui.visibility: ["app"]`
- removes Apps-specific `_meta.ui` and legacy `_meta["ui/resourceUri"]` fields
- rejects direct calls to app-only tools
- rejects unlisted `ui://` resource reads

Direct server routes and group or aggregate routes use different tool names. See below.

## Tool Names

Direct server routes such as `/mcp/weather-station` expose upstream tool names unchanged, such as `forecast`, regardless of client Apps support or upstream idle state. MCPHub removes only its own prefix; prefixes in upstream tool names remain intact.

Group and aggregate routes keep qualified names (`weather-station::forecast`), even with only one member. Group aliases and the configured name separator still apply. Apps widgets on these routes should use the qualified name from the tool listing or host context.

Previously advertised raw and qualified names remain callable where the route resolves them unambiguously, subject to the same tool visibility and access restrictions. On direct routes, upstream raw names take precedence over colliding legacy qualified aliases, including names such as `call_tool`, `search_tools`, and `describe_tool`. Apps support still controls Apps metadata and app-only tool visibility.

## UI Resources

MCP Apps servers may omit UI-only resources from `resources/list`. On an Apps-eligible route, MCPHub forwards direct `resources/read` calls for unlisted `ui://` URIs:

- On a single-server route, the request goes straight to that server.
- On a multi-server route, MCPHub has no prior way to know which upstream owns a given `ui://` URI, since it isn't listed. It probes each connected server in the group in turn and returns the first successful response.

Ordinary listed resources remain readable, but Apps-specific metadata is removed outside Apps-eligible routes.

## Dynamic Lists

MCPHub subscribes to upstream `tools/list_changed`, `resources/list_changed`, and `prompts/list_changed` notifications. It refreshes its cache, updates Smart Routing embeddings for model-visible tools, and notifies connected downstream clients.
